# 多设备同步（应用层方案）

> **讨论入口**：本文档是「现有内核如何搭配应用软件实现多设备同步」的讨论落点。后续关于同步拓扑、传输、调度、失败处理、应用侧职责、设备生命周期等细节，直接追加到本文档（见文末「讨论记录」），不要散落在聊天或临时文件里。
>
> 内核契约以 `SPEC.md` / `api.md` / `data.md` 为准；实现细节以代码与 `.design/changes/` 为准。本文不改变内核 API、存储格式或 ABI。

## 一句话方案

> 每个设备各自持有一份完整库；应用自己搬 `SHY2` 帧；内核负责解密、合并、游标和冲突收敛。没有中心协调者。

---

## 1. 角色与状态

```
 设备 A（安装 A）                          设备 B（安装 B）
┌──────────────────┐   SHY2 帧（不透明）  ┌──────────────────┐
│ shio 库 A         │ ──────────────────▶ │ shio 库 B         │
│ device_id = A     │ ◀────────────────── │ device_id = B     │
│ db_id     = 同一逻辑库                  │ db_id     = 同一   │
│ shio.changes(A)   │                     │ shio.changes(B)   │
│ peer/B, heard/B   │                     │ peer/A, heard/A   │
└──────────────────┘                     └──────────────────┘
        ▲                                         ▲
        └──────── 应用自己的传输（WS/HTTP/中继/BLE/文件）──┘
```

- **`db_id`**：逻辑库 ID，配对/克隆时复制；同一个 `db_id` 的所有设备属于同一同步组。
- **`device_id`**：每个安装独立生成；`clone_backup` 会换新的，`restore` 保留旧的。
- **`peer/<device>`**：本机在对方日志里的已消费游标（每个对端一个）。
- **`heard/<device>`**：对方告诉本机「我已读到你的日志哪一条」，用于裁剪。
- **`cur/<device>`**：对方公告的当前写 key。
- **`shio.changes`**：本机产生的变更日志（记录 + 控制项），是发给别人的东西。

内核不做网络、不做后台线程、不做发现；它只提供「给我一页变更 / 应用一帧 / 告诉我对方读到哪」的原语。

---

## 2. 首次入组：两条路

### A. 配对（推荐，正常加设备）

1. 已有设备 A 调 `create_pairing_offer(ttl)`，得到 `PairingOffer { frame, secret, fingerprint }`。
2. 应用把 `frame + secret` 编成二维码（或局域网直传），并让用户核对 6 位 `fingerprint`。
3. 新设备 B 用 `open_with_pairing(options, credential, offer, secret)` 建库：**目标必须不存在或为空**，B 得到相同的 `db_id` 和完整 key 链，但**不包含记录**。
4. B 向 A 拉日志：A 的日志基线（`enable_sync` 或克隆时重建）包含全部记录 + `CurrentKey`，B 从 0 拉到末尾即得到全量数据。若 A 的日志已裁剪，则改走快照（见 §5）。

配对包只带身份与密钥，不带记录——所以「只靠配对包就有数据」是不成立的，必须再拉日志/快照。

### B. 克隆（把整库复制到第二台设备）

`clone_backup(backup, target, password)`：保留 `db_id`、key 链和记录，**换新 `device_id`**、清空设备级同步状态、按新身份重建完整日志。适合「换手机、从备份文件恢复出第二台设备」。恢复后它可以和原设备同时在线同步。

> 不要用 `restore` 做这件事：`restore` 保留 `device_id`，两台同时运行会出现重复身份，`peer/`、`heard/` 和日志 `writer` 全乱。

---

## 3. 稳态同步：应用驱动的拉取循环

对每个对端，应用维护一个「连接 + 游标」的状态机。最小循环（伪代码）：

```rust
let sync = kernel.sync()?;

// 1) 推送：把本机日志里对端还没读的部分发出去
let after = sync.peer_cursor(peer.id)?.unwrap_or(0);
let page = sync.changes_since(after, 100)?;   // 一页最多 1000 条
let frame = sync.encode(&page)?;              // SHY2 变更页
transport.send(peer, frame).await?;

// 2) 拉取：收到对方帧后应用（整页一个事务，推进 peer/<sender>）
let frame = transport.recv(peer).await?;
sync.apply(&frame)?;                          // 幂等；落后游标会报 SyncResyncRequired

// 3) 回报进度：告诉对方「我读到你的第 N 条了」，它才能裁剪
let progress = sync.progress_frame(peer.id)?; // 本机在对方日志中的游标
transport.send(peer, progress).await?;

// 4) 周期性裁剪（所有对端都报过进度后才会真正删）
sync.compact_changes_auto()?;
```

要点：

- **双向**：每个方向各有一条日志、一个游标；不是「服务器广播」，而是成对同步。
- **每页原子**：`apply` 在一页内一个写事务；失败不会留下半页。
- **幂等**：重复帧、乱序帧都安全；游标只增不减。
- **断点续传**：游标在 `shio.sync` 里，进程重启后从 `peer_cursor` 继续。
- **帧大小**：单帧 ≤ 4 MiB，单页条目 ≤ 1000；大库要分页。
- **应用负责重试**：网络断了就按游标重发，不需要内核参与。

---

## 4. 冲突：LWW，没有向量时钟

- 冲突判定是全序 `(updated_at, rev, blob)`：时间戳大的赢，相同再比 `rev`，再相同比密文字节。
- 同步启用后，本机写入的 `updated_at = max(now, 上一条 + 1)`，保证本机每次写入都严格新于自己上一次；跨设备仍以设备时钟为准。
- 结果是**最终一致**：只要所有帧最终送达，各设备收敛到同一个版本。
- 代价：
  - 时钟偏差会偏向「表快」的设备；
  - 没有「保留两份/人工合并」的原语，业务层如需冲突 UI 要自己做；
  - 删除是墓碑（同步模式下禁止 `purge`），删除也参与 LWW。

---

## 5. 日志裁剪与快照重同步

**为什么要裁剪**：`shio.changes` 只增不减，长期运行会膨胀。

**裁剪门控**：`compact_changes_auto()` 的「已知对端」= `cur/` ∪ `heard/`（排除本机）；只要有一个对端没有 `heard/`，就返回 0。所以应用必须**定期把 `progress_frame` 发给每个对端**，对方 `apply_progress` 后写入 `heard/`。

**落后于裁剪点**：对端用 `changes_since` 拉取时，如果游标 < `log_start`，返回 `SyncResyncRequired`。此时不能重试，要走快照：

1. `snapshot_start()` 取一个日志序号；
2. 循环 `snapshot_page(after, limit)` → 编码成帧 → 对端 `apply_snapshot`（LWW 合并，写入记录日志以对端自己的 `device_id` 为 writer）；
3. 快照完成后，对端从该序号继续增量。

快照是**一致性兜底**，不是备份：它只搬记录，不带身份、游标或密钥链。

**退场设备**：如果某设备永远不再回来，它的 `cur/` / `heard/` 会永久卡住裁剪。用 `forget_device(device)` 删除它的 `peer/`、`cur/`、`heard/`、`ack/`、`mig/`；它若回来会重新登记，必要时走快照。

## 6. 密钥轮换（多设备）

任何设备都可以发起：

1. `begin_rotation()`：生成新 key `to`，写 `rot/<to>` 和日志控制项，切换本机写 key。
2. 对端拉到新 key 的 `CurrentKey` 时若缺 key，返回 `RotationRequired`；应用调用 `rotation_offers()` 取 offer 并 `apply_offers`，对端安装 key 并回 `ack/<to>/<device>`。
3. 各设备 `migrate_all(to)`（或 `migrate_tick` 合作式推进）把旧记录重加密，完成后公告 `Migrated`。
4. 所有已知设备都 ack + 迁移后，`retire_key(from)` 删除旧 key；`prune_rotation_offers(to)` 清 offer。

特点：无中心、可并发（不同设备可能生成不同 `to`，按 `(created_at, key_id)` 收敛）；轮换期间读写照常，只是新写入落到新 key。

## 7. 设备生命周期

| 场景 | 做法 |
|---|---|
| 新增设备 | 配对（`open_with_pairing`）→ 拉日志/快照 |
| 换手机、旧机还在 | 新机配对或 `clone_backup`；旧机 `forget_device` 前确认数据已同步 |
| 旧机已经没了 | `clone_backup` 从备份恢复（新 `device_id`），或在其他设备上把它 `forget_device` |
| 同机灾难恢复 | `restore`（保留 `device_id`），**不能**同时跑第二份 |
| 只想看数据 | `shio-tool export` / 只读打开 |

## 8. 应用侧必须自己做的事

内核只给你「帧 + 本地状态」，以下都在应用：

1. **传输与连接**：WebSocket / HTTP 长轮询 / 局域网 mDNS / BLE / 文件中转都行；帧是不透明字节，别自己解析。
2. **安全**：TLS/证书固定；配对二维码的 `secret` 和 6 位指纹要带外核对；内核不提供传输层加密。
3. **发现与账号**：谁和谁是同一库、哪些设备在线、如何找到对方。
4. **调度**：前后台、充电、网络类型；同步频率；批量大小。
5. **快照编排**：检测 `SyncResyncRequired`，拉快照并应用。
6. **轮换编排**：`RotationRequired` 时交换 offer；迁移可放到空闲时用 `migrate_tick`。
7. **进度回报**：定期发 `progress_frame`，否则裁剪永远为 0。
8. **设备管理 UI**：设备名、指纹、删除/解绑、离线标记。
9. **冲突策略**：内核是 LWW；要「保留两份」只能在业务层加字段/副本。
10. **时钟**：建议设备用 NTP；LWW 的可信度取决于时钟。

## 9. 拓扑选择

- **全互联（full mesh）**：每对设备独立同步，简单，N 台设备最多 N(N-1)/2 条连接，但每对互不依赖。
- **星型/中继**：一台常在线设备（或服务器上的一个 shio 实例）作为 hub，其他设备只和它同步；hub 也是普通成员（有自己的 `device_id`），只是连接数少。
- **纯中继（不解除密）**：内核对帧的加解密是端到端的（帧里是密文/密钥材料），理论上可以让不持 key 的中继只转发字节；但中继仍要按「每个对端」保存游标和待发队列，实际复杂度接近一个成员节点。首版更建议「中继 = 一个成员」。

---

## 10. 已知边界

- 没有设备签名/撤销、没有最小权限：拿到 key 链的对端可以读全部数据、写任意记录。
- `forget_device` 只是本机遗忘，不是远程踢人。
- 没有 HLC/向量时钟：跨设备时钟偏差会影响胜负。
- 没有内建后台任务、推送、发现、TLS。
- 裁剪依赖对端上报；长期离线又不上报的旧设备会卡住裁剪，需要 `forget_device`。
- 帧与页面有上限（4 MiB / 1000 条），大库需要分页与快照。
